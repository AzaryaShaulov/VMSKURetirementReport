Upgrade and Modernization ScenariosRecommended steps for each migration path, with examples and Microsoft Learn links, including SCSI to NVMe conversion and Gen1 to Gen2 (Trusted launch).

The general VM sequence below is for customer-managed VMs. For AKS, use the AKS Node-Pool Replacement scenario instead: do not resize backing VMs/VMSS directly or run standalone Gen1/NVMe conversion utilities on AKS-managed nodes. This is educational guidance, not an AKS inventory or pool-readiness assessment by this tool.

  1. Confirm the retirement and the Microsoft-recommended target series for each retiring size.
  2. Check prerequisites: Gen1 VMs need the Trusted launch upgrade before a Gen2-only size; SCSI VMs need NVMe conversion before an NVMe-only size (validate guest OS support first).
  3. Request quota for the target family and regional vCPUs (see Quota Actions). Use peak demand when source and target must coexist.
  4. Resize in a change window, then validate disks, networking (MANA), temp-disk usage (keep a d size if the workload needs local scratch) and application health.

Recommended steps by migration path

PathWhen it appliesExampleRecommended steps
Direct ResizeThe target already supports the VM's hardware generation and disk controller.Standard_D4s_v5 → Standard_D4s_v6
  1. Request target-family and regional vCPU quota (size list)
  2. Back up or snapshot the OS and data disks
  3. Resize in a change window; the VM restarts (resize a VM)
  4. Validate the application, disks and networking
SCSI to NVMe + ResizeThe target supports NVMe only and the VM uses SCSI.Standard_D4ds_v5 → Standard_D4ds_v6
SCSI to NVMe
  1. Confirm the guest OS image supports NVMe (supported images)
  2. Test on a clone or snapshot first; reference Linux disks by UUID, not device name
  3. Convert the disk controller to NVMe and resize (conversion steps)
  4. Check that every disk is visible, then validate the application
Gen1 + NVMe + ResizeA Gen1, SCSI VM must move to a Gen2, NVMe-only size.Standard_DS3_v2 → Standard_D4s_v6
Gen1 + SCSI to Gen2 + NVMe
  1. Check the OS supports the Trusted launch upgrade (Gen1 upgrade); if not, redeploy instead
  2. Back up the VM; plan for a restart and MBR to GPT conversion
  3. Upgrade to Gen2 (Trusted launch), then convert the disk controller to NVMe
  4. Resize to the target and validate boot, disks and drivers (MANA networking)
Gen1 Modernization + ResizeA Gen1 VM must move to a Gen2-only size; the controller stays SCSI.Gen1 VM → Gen2-only size
  1. Check OS and size support for the Trusted launch upgrade
  2. Back up the VM and plan the restart
  3. Upgrade Gen1 to Gen2 (Gen2 support)
  4. Resize to the target and validate
Redeploy / Rebuild ReviewThe guest OS cannot be upgraded in place (for example Windows Server 2016, Debian, Azure Linux).Gen1 VM (unsupported OS) → New Gen2 VM
  1. Build a new Gen2 VM on the target size from a supported image
  2. Move data disks or restore from backup, then cut over
  3. Keep the old VM until the workload is validated, then delete it
AKS Node-Pool ReplacementAn AKS system or user node pool uses a retiring VM size.Retiring node pool → Supported replacement pool
  1. Confirm retirement scope and an AKS-supported target SKU, OS and zones; check target-family/regional quota, allocation capacity and subnet/pod IP headroom while both pools coexist (AKS limits)
  2. Create replacement capacity through AKS, preserving required labels, taints, autoscaler, disk and pod settings; replace a system pool with another eligible Linux System pool before removing it (system pools)
  3. Validate scheduling, node selectors/affinity, topology, networking, DaemonSets and persistent-volume attachment; confirm replicas and PodDisruptionBudgets permit eviction
  4. Cordon and drain old nodes progressively; emptyDir and other node-local data are not migrated automatically (replacement workflow)
  5. Verify application and system-pod health before removing the old pool; adding a System pool alone does not move existing system pods
  6. Update infrastructure-as-code and autoscaling settings so the retiring SKU is not recreated; no automatic SKU migration or zero-downtime guarantee

Examples are illustrative. The path, target and blockers for each VM are in the VMs with Retiring SKUs table and its details; guest readiness cannot be proven from Azure control-plane data, so always test before changing production.
